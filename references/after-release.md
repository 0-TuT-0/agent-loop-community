# 发布之后：问题、小优化、新需求

阶段合并推送之后进来的工作，都由总控直接写票、标风险，走同一条修复分支。不回到 `/wayfinder` 和 spec；用户要求重新讨论时除外。

## 从哪里进来

需求和问题的入口只有三个：

- **用户直接对总控说**：使用中发现的问题、体验优化、新需求。用户过待办清单时决定「开成票」的条目也属于这一条（[todo.md](todo.md)）。
- **错误对接窗口**：用户贴报错，它定位后经用户同意通知总控（[optional-windows.md](optional-windows.md)）。
- **回归测试的结果**：总控运行 `agent-loop regress`，读各阶段结果里的失败项（[regression-test.md](regression-test.md)）。

其他窗口（开发、计划、审计、合并、写测试文档、规范维护）收到与自己任务无关的需求时，不处理也不转达，只告诉用户：「这件事请对总控说，或者开错误对接窗口」。总控从这三个入口之外收到转达的需求时，先向用户本人核实，再动手。

总控给每个进来的问题一个编号，写进开发计划的进展记录。

新需求与参数文件「用户维护的文档」里的某一条冲突时，先停下来请用户决策；用户表态后由总控更新那份文档并留记录，再写票派工（`SKILL.md`「护栏」）。没有冲突的新需求直接写票派工：写完票就开它的第一个窗口，参数文件「自动接续」取「需确认」时也不用再问用户（`dev-phase.md`「6. 自动接续」）。

## 票和分支

- **票**：放在所属阶段的 `<阶段目录>/issues/` 里，接着已有编号往后排。每张写明来源（用户原话、问题编号，或对应的测试项编号）、现状、要求、涉及模块、风险和执行链；修的是某张已完成的票留下的问题时，用 `agent-loop ledger source <修复票> <来源票>` 记进票台账；有几种做法可选时，列出方案，由用户选定后再开工。
- **修复分支**：一条（名称见参数文件），第一次用时从当前 feature 分支开出，集成 worktree 是 `<worktree 根目录>/fix-integration`。它的角色和阶段分支一样，窗口不直接在它上面改代码。
- **票分支**：每张票从修复分支最新提交开 `<修复分支>-<NN>` 和自己的 worktree，用 `agent-loop ticket open <票> --fix --prompt <提示文件>` 一次建好并开窗；合回修复分支用 `agent-loop ticket merge <票>`。互相没有依赖、不改同一个文件的票可以并行；总控按完成的先后依次以 `--no-ff` 合回修复分支。要改同一个文件的票用 `Blocked by` 排成先后。
- **优先级**：修复分支上的票优先于下一阶段的票。

## 每张票怎么做

和普通票同一规则，看两个条件：

| 条件 | 做法 |
| --- | --- |
| 风险：中、低 | 一个窗口直接改 |
| 风险：高 | 先出计划、用户审定，再开发（`dev-phase.md` §4） |
| 改动了已审定的 spec（推翻或修改其中的口径、数值、接口） | 另外多做两件事，见下 |

**改动了已审定 spec 的票**：

1. 开发完成后，先在**票分支**上单独审计一次，审的是票分支相对它基点的改动，方式同阶段审计（[stage-audit.md](stage-audit.md)），报告写到 `<阶段目录>/reviews/<NN>-audit.md`。审计通过后才合入修复分支。这样修复分支上始终是可以发布的内容，其他票不用等它。
   审计开出的修复照阶段审计的做法另开修复票，不在原票里返工：用户对审计结论逐条表态后，总控新建一张修复票（接着已有编号），写明修的是哪张票的哪几条审计问题，并运行 `agent-loop ledger source <修复票> <原票>`。原票还没合入，所以修复票不另开分支，就在原票的分支和 worktree 上接着改；开窗时写 `--step fix --ticket <修复票> --dir <原票的 worktree>`。修复票完成后，原票分支才合入修复分支，两张票各记一次 `agent-loop ledger done`。原票不记返工。
2. 总控在对应阶段的 spec 末尾追加修订记录：改了哪条、旧值和新值、依据哪张票和用户的哪个决定。

## 合并与后续

- **合并**：修复分支攒几张票一起走一次合并窗口（[merge-window.md](merge-window.md)），合入来源是修复分支。什么时候合由用户决定。
- **带到下一阶段**：修复合入 feature 分支后，总控把 feature 分支以 `--no-ff` 合入正在开发的阶段分支；有冲突时停下交给用户。
- **重测**：启用了回归测试时，修复上线后只复测对应的测试项和计划里写明受影响的项，结果在 `<阶段>-result.md` 里追加成新的一轮（[regression-test.md](regression-test.md)「收口」）。
- **对下一阶段的影响**：问题涉及接口契约、数据模型或设计变更时，总控判断下一阶段哪些票受影响，写进这些票的 `## Comments`，并通知进行中的窗口。需要改下一阶段 spec 的，交给用户决定。

完成标准：每个进来的问题都有编号，并且落在一张票上，或者有用户「不处理」的决定记录。
