# 初始化（bootstrap）

初始化分三层，由下往上，每层做一次。重复执行是幂等的：已有的配置和规则保持不变，指针只保留一份。

| 层 | 什么时候做 | 产物 |
| --- | --- | --- |
| **本机** | 每台电脑一次 | `$AGENT_LOOP_HOME/machine.md`（默认 `~/.agent-loop/machine.md`）：依赖、宿主能力、引擎适配表、运行目录根位置 |
| **项目** | 每个项目一次 | `docs/agents/loop-profile.md`、规范入口指针、协作流程冲突的处置、本机排除 |
| **功能** | 每个新功能一次 | 功能目录、阶段分支、总控所有权、入口选择（见 SKILL.md「入口」） |

## 本机初始化

先按仓库的 [README](../README.md) 注册当前宿主的 skill 入口。从目标项目的新会话显式调用，Codex 用 `$agent-loop`，Claude Code 用 `/agent-loop`。下文命令以已加载的 skill 目录为基准，如 `"$HOME/.agents/skills/agent-loop/scripts/bootstrap.sh" machine`。

1. 运行 `scripts/bootstrap.sh machine`：检查依赖（git、bash、perl，以及可选的 osascript、iTerm2）、本机可用的引擎和版本，然后生成 `machine.md`。已经存在时只报告差异，不覆盖。
2. **宿主唤醒实测**：按当前宿主和版本分别记录，例如 Codex 桌面、Codex CLI、Claude Code。用该宿主支持的后台完成通知挂一个延迟 5 秒的命令，核实结束本轮后它能否把结果送回同一会话并触发下一轮处理。验证成功填 `auto` 并记录方法；仅能在当前轮等待、需要用户回来或尚未验证时按 `manual` 运行，注明原因。旧配置里没有宿主名称的实测值只归给能确认的原宿主。
3. **引擎适配表**：每个要用的引擎填一行，字段说明见 `engines.md`。先用 `--help` 核实参数，再填写。启动命令模板里，推理强度用 `{effort}` 占位。
4. **可选扩展**。如果项目使用外部讨论、规格编写或拆票工具，在对应宿主核实可用性，再把名称和调用方式手工记入本机配置。有现成票时可直接接入，也可以按本 skill 的票模板拆票。
5. **权限放行**（可选）：使用当前宿主的沙箱和审批机制。模板末尾的 `Bash(…)` 仅适用于 Claude Code。

完成标准：`machine.md` 中宿主能力是实测值，至少一个引擎有完整的一行。

## 项目初始化

### 1. 只读发现

- **新项目先建仓**：目录还不是 git 仓库，或者仓库里一个提交都没有时，worktree 建不起来。经用户同意后，运行 `scripts/bootstrap.sh init-repo <目录>`：它会执行 `git init`，并做一次空的初始提交。
- 运行 `scripts/bootstrap.sh discover <仓库>`，读它列出的规范入口和规范目录。整理出以下各项，每项注明来源：
  - **规范入口**：tracked（随 git 共享）、local（本机）还是 ignored（被忽略）；是否已经有 agent-loop 指针；
  - **任务来源**：用什么任务跟踪方式，分诊状态有哪些取值；
  - **验证命令**：怎么跑测试，有没有回归基准；
  - **集成策略**：交付到本地分支、PR，还是直接推送；
  - **与本机配置不同的引擎需求**。
- 运行 `scripts/bootstrap.sh tracker <仓库>`，查看仓库里已有的任务跟踪说明。若项目使用其他位置或跟踪系统，将其说明入口和票文件约定记入 profile。

只向用户确认推断不出来、而且会影响授权或验收的事：是否允许本地提交；交付终点是什么；哪些环境是共享资源；推送和写外部资源的授权。

### 2. 协作流程冲突

项目里可能已经有一套多窗口或多 agent 的协作流程，例如别的总控规范。如果常驻入口指向这类流程，worker 会同时收到两套指令：写哪个状态字段、向谁回报、怎么开窗。

1. 运行 `scripts/bootstrap.sh conflicts <仓库>`。它会列出常驻入口及其指向的每份文档，按关键词的命中数给出初步判断：
   - **协作流程候选**：定义了总控、回报、开窗、票状态、派工的；
   - **需要人工判断**；
   - **业务规范**：数据库、前端、领域规则等。
2. 总控逐份阅读「协作流程候选」和「需要人工判断」的文档，确定哪些是协作流程。
3. 有协作流程时，只问用户一个问题：

   | 选项 | 做法 | 适用 |
   | --- | --- | --- |
   | **A. 划定范围（推荐）** | 在原流程的入口条目上加一句适用条件，例如「只适用于 <原总控> 管理的讨论记录和票目录」；同时在 agent-loop 指针里写明本功能使用 agent-loop | 两套流程并存 |
   | B. 由 agent-loop 接管 | 原流程的入口条目改为指向 agent-loop | 准备整体切换 |
   | C. 不改入口 | 只靠初始提示中「冲突时以本票生效规则为准」，以及监视的 `status-mismatch` 兜底 | 入口文件归团队、不便修改时；可靠性最低，选之前要告诉用户 |

4. 把选择和协作流程文档的清单记进 `loop-profile.md`「协作流程冲突」一节，以后不再重复询问。入口文件被 git 跟踪时，A、B 两项都按团队接入处理：先经用户同意，再按项目原来的审查流程提交。
5. 参数文件的「项目规范」只列业务规范，不列协作流程文档。

新项目通常没有冲突，这一步可以直接跳过。

### 3. 建最小 profile，注入规范入口

1. **建 profile**：按 `templates/profile.md` 建 `docs/agents/loop-profile.md`。首次只要求填：
   - 任务来源、工作区；
   - 运行目录（默认 `~/.agent-loop/runs/<项目>/`，在仓库之外）；
   - 规范入口、业务规范清单；
   - 验证命令；
   - 已授权的交付终点；
   - 本阶段各环节使用的引擎、模型与推理强度，以及相对 `machine.md` 的覆盖。

   没有数据库、没有发布、没有阶段划分的项目，对应的章节不填。
2. **注入规范入口**：派出的 worker 和用户手动开的窗口要读到同一份规范。
   - **Codex 本机接入**：对主工作树和每个使用 Codex 的 worktree 执行 `scripts/bootstrap.sh codex-entry <工作树> <指针内容文件>`。命令按该树的实际情况更新 `AGENTS.md` 或优先生效的 `AGENTS.override.md`，并精确排除生成的本机入口。若为保留已跟踪的 `AGENTS.md` 而新建 override，指针会要求先读同目录的团队规则。已有生效的 override 则保留原有优先级。若生效入口本身已跟踪且无法本机注入，记录限制，派工时在初始提示中给出规范路径；需要手动会话也自动加载时，由用户决定是否团队接入。
   - **Claude Code 本机接入**：用 `scripts/bootstrap.sh inject <工作树>/CLAUDE.local.md <指针内容文件>` 更新本机入口。
   - **团队接入**：经用户同意，给 Codex 用 `codex-entry --team`，给其他引擎用 `inject --team`。团队指针应指向所有协作者可获取的规则，按项目原有流程审查后提交。
   - 指针内容包括：读 `loop-profile.md` 和业务规范清单；涉及票时，先读票文件协议和本票生效规则；认领票要经过总控。若项目配置了 Codex 自定义后备规范文件名，在引入首个标准入口时也指回原先生效的文件。
3. **本机排除**：对其余本机专用文件运行 `scripts/bootstrap.sh exclude <仓库> <具体文件>…`。在 profile 记录各宿主的入口、指针内容文件的位置，以及跨树复制的文件清单。
4. **worktree 同步**：建 worktree 或修改本机规范后，仅对约定由主工作树独占维护的文件执行 `scripts/bootstrap.sh sync <仓库> <具体文件>…`。例如只同步 `docs/agents/loop-profile.md`。Codex 入口按第 2 步逐树注入；保留各分支自己的入口和其他项目文件。
5. **验证入口**：在目标 worktree 打开新的 Codex 或 Claude 会话，确认能找到 profile 和原有项目规范。没有项目入口机制的其他 CLI，在 profile 记录限制，派工提示带上全部生效规则。

完成标准：在一个新建的 worktree 里，用户手动打开受支持的引擎，它能说出本项目规范入口的位置；`git status` 中不出现任何本机专用文件。

### 4. 新项目的第一张票

项目还没有测试框架和验证命令时，第一张票固定为「脚手架与测试框架」：
- `Deliverable: commit`，风险标 `medium`；
- 产出：项目骨架、测试框架、一个能跑通的示例测试，以及写进 profile「验证命令」一节的定向测试命令和全量测试命令。

这张票验收之前，其他开发票都依赖它（`Depends`）。

### 5. 用一张低风险票走通完整协议

这个验证进入功能层。在用户要求派工且已有可用引擎和测试票时执行。

1. 建一张 `Deliverable: commit`、`Risk: low` 的小票（新项目就用第 4 步那张）。
2. 按 SKILL.md 的「启动」和「循环」完整走一遍：
   - `loopctl acquire`；
   - 认领、派工；
   - 让 worker 故意提请一次裁决，送回后确认 worker 写了 `Ack`；
   - worker 完成，验收，集成，`accepted`。
3. 把实测结果补进 `machine.md` 的引擎行：提示传入方式、送回方式能否送达（`message` / `queue` / 只能 `restart`）、能否读到规范入口。
4. 再测两个恢复场景：
   - 派工后立刻关掉总控、重新打开：同一张票只启动一次；
   - 验收完成后再挂一次监视：同一个事件不会再报。

完成标准：这张票 `accepted`；引擎能力是实测值；两个恢复场景都通过。

### 6. 按需打开并行和阶段模块

- **打开并行前**：同时派两张没有文件冲突的票，确认它们能同时推进；再派一张和在途票有冲突（`Touches` 重叠）的票，确认它会被阻塞。
- **启用阶段流水线前**：先跑一张无提交的产物票，按 `artifact` 验收；再模拟审计只有部分条目获批，确认已获批的修复可以派工、待定的保持待定。
- **离线自检**：任何时候都可以运行 `tests/loop-behavior.sh`。

完成标准：参数文件中只有实测通过的模块标为「启用」。
