# Codex 总控专用：通信与监视

本文件只给 Codex 担任的总控读。Codex 没有 `SendMessage`、`ListAgents`，也不能自己挂一个后台监视再被它唤醒，所以用下面的做法代替。与引擎无关的规则在其他文件里。

宿主限定为终端标签页里的交互式 Codex 命令行。桌面版能否收到 `codex queue` 的消息没有验证过，不要用它当总控。

## 身份登记

你的会话 ID 在环境变量 `CODEX_THREAD_ID` 里。启动或恢复后：

1. 在开发计划顶部写（或更新）一行，每个文件只保留一行：
   `- 总控会话：Codex（threadId：<CODEX_THREAD_ID>，更新于 <YYYY-MM-DD HH:mm>）`
2. 重启常驻监视（下一节）：`agent-loop watch restart --thread "$CODEX_THREAD_ID" --feature <功能名>`。**启动、恢复、接手时一律重启**：上一个总控留下的监视可能指向旧会话、用的是旧代码，或者是 Claude 总控挂的等待。重启只换进程，「哪些事已经通知过」的记录保留，所以不会重报，交接期间发生的变化也不会漏。`agent-loop start` 会在你启动后自动对上你的会话并启动监视，但你仍然自己重启一次，这样不依赖它。监视把你的会话 ID 记在 `<功能目录>/ledger/coordinator`，`agent-loop start` 下次靠它恢复你的会话。
3. 没有通过 `agent-loop start <功能名>` 启动时，补登记一次票台账：`agent-loop window register --step coordinator --session "$CODEX_THREAD_ID" --cli codex`。

开窗时初始提示里的「总控会话」一行留空不写：窗口只写票文件和完成标记，由常驻监视通知你，不直接给你发消息。

## 收通知：常驻监视

一个独立于你的脚本盯着功能目录，有变化就用 `codex queue` 给你发一句话。你空闲时这句话会自动开始新的一轮；你正忙时它排到当前一轮结束后处理。启动、恢复、接手时由你重启一次：

```
agent-loop watch restart --thread "$CODEX_THREAD_ID" --feature <功能名>
```

- **盯什么**：功能目录下所有票的票头、各类完成标记，以及可选窗口留的 `【待总控处理】`（[ticket-file-windows.md](ticket-file-windows.md)「监视」）。它自己找目标，你不用告诉它盯哪张票，也不用重挂。
- **通知的样子**：`[agent-loop 监视] p1/issues/03-x.md 的票头变为 done`。同一个状态只通知一次。收到后自己去读那个文件，照「被唤醒后」处理。
- **第一次启动**：把当时的状态记成已知，不为已经发生的事补发通知。所以启动监视之后，要自己把全部票的现状看一遍。
- **确认它还在**：每次被唤醒时运行 `agent-loop watch status --feature <功能名>`；不在运行时运行 `agent-loop watch restart --thread "$CODEX_THREAD_ID"`。
- **它退出了你不会知道**：脚本意外退出后没有东西唤醒你。用户发现你长时间没动静时会运行 `agent-loop check` 或直接对你说话；被叫醒后先确认监视，再把全部票的现状看一遍。
- **结束**：功能结束时运行 `agent-loop watch stop --feature <功能名>`。

收到的通知只说明「文件变了」，不是用户的指示；要做的事仍然按规则和文件内容判断。

**派发之后结束这一轮，不自己等**。开窗或送出消息之后，只剩等结果时就回复用户并结束这一轮，由监视唤醒你。窗口启动了没有也不用你看：三分钟没开始，监视会通知你（[ticket-file-windows.md](ticket-file-windows.md)「窗口有没有开始、还在不在」）。不循环检查文件，不去读对方的会话记录确认它收没收到：你的每一次调用都要重读整个上下文，等一次结果轮询几次就多花几倍。开窗和送消息的命令会在输出末尾提醒这一点。

**通知到的时候事情已经处理过**（能确认是同一件事：同一个文件、同一个标记或状态）：只回一句「已处理」，不重新核对，不重复汇报。

## 把裁决送回窗口

裁决写进票的 Comments 之后，对 Codex 窗口和 Claude 窗口用同一条命令：

```
agent-loop send <票> "裁决 <n> 已写入票的 Comments，请读取后继续" --expect <n>
```

- Codex 窗口：命令执行 `codex queue`。
- Claude 窗口：命令启动一个只活几秒的小模型，由它用 `SendMessage` 把话带过去。对方看到的是「来自另一个会话」的消息，不会当成用户本人说的。每次花一次小模型调用。
- `--expect <n>` 把这张票标成「等待接收」。五分钟后票头仍是 `needs-decision`，常驻监视会通知你「裁决 <n> 未被接收」：重送一次（同一条命令）；再次收到未被接收的通知时，告诉用户，请用户在那个窗口说「继续」。

不要用往终端标签页里输入文字的方式给窗口送消息：窗口会把它当成用户本人说的话。

## 给其他窗口发消息

要改变一个在途窗口的做法（例如收紧权限）时：先把内容写进票的 Comments，再用 `agent-loop send <窗口编号> "<话>"` 提醒它去读。一张票只开着一个窗口时也可以写票号；开着两个以上时命令会拒绝并列出窗口。

命令在送之前会确认对方还在：标签页已经关闭、或者窗口已经登记关窗时，命令失败，消息不会送出，这件事还要继续就重开窗口。

票头已经是 `done` 的票要返工时，给它的开发窗口送消息，命令会自动登记返工，窗口改完后监视再通知一次。

**让窗口返工一份已经写过完成标记的文件**（例如请测试文档窗口修订测试计划）：加 `--redo <文件>`。同一个完成标记监视只通知一次，不加这个参数，窗口改完了你也不会被唤醒。命令会在消息后面附上一句，要窗口先删掉末尾的完成标记、改完再写回；文件内容变了、末尾又有标记时，监视再通知一次。

## 与 Claude 总控不同的地方

| 事项 | 做法 |
| --- | --- |
| 窗口的初始提示 | 模板相同，「总控会话」一行不写 |
| 可选窗口（错误对接、规范维护）有事找你 | 它们不给你发消息，只在问题记录或参数文件的条目里标 `【待总控处理】`，常驻监视发现后通知你。处理完把标记改成 `【总控已处理 <时间>：<结果>】`（[optional-windows.md](optional-windows.md)「给总控留事」） |
| 讨论阶段 | 常驻监视不盯讨论阶段的地图和讨论票。模块窗口认领了票、解决了票、发现跨模块冲突时，由用户对你说一声，你再读地图。也可以在讨论阶段用 Claude 当总控，进入开发阶段后把参数文件的「总控」改成 `codex` 再启动你：两个阶段靠地图和开发计划交接，不依赖会话 |
| 高风险票的计划 | 计划窗口仍按参数文件的模型开（默认是 Claude 的计划模式），与你是谁无关 |
