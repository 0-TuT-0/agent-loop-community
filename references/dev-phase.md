# 开发阶段：spec、拆票、开发、接续、收尾

路径、分支名、模型、测试命令都从参数文件取。下文用 `<阶段>` 表示阶段代号（例如 `p3`），`<NN>` 表示两位票号，`<阶段目录>` 表示 `<任务目录>/<功能>/<阶段>/`（目录结构见 [dev-plan.md](dev-plan.md)「目录」）。

## 1. 阶段 spec

- 开一个 spec 窗口（模型见参数文件），工作目录是上一阶段合并后的集成 worktree；第一个阶段用主工作树。它只读代码，产出 `<阶段目录>/spec.md`。
- 决策已经在讨论阶段由用户确认，spec 窗口只综合，不重新讨论。发现决策缺口或冲突时回报总控，由总控交给用户裁决。
- 开 spec 窗口之前，总控先展示待办清单的全部未处理条目，请用户逐条表态（[todo.md](todo.md)）；去向是「并入 spec」的条目，写进给 spec 窗口的初始提示。
- spec 要承接开发计划的跨阶段前提，以及待办清单里并入本阶段的条目。
- spec 写明三节：对后续阶段的承诺（接口与数据结构）、回归与隔离（参数文件列出的隔离对象）、已接受的差异。
- 用户审定 spec，审定记录写在 spec 末尾。审定完成后，spec 窗口在 spec 的最后单独写一行「spec 已审定」，再通知总控。总控开 spec 窗口时就把 `spec.md::spec 已审定` 加进监视：消息没发出来（窗口中断、电脑休眠）时，靠这一行发现。

**通知总控**在本 skill 里统一指：先把结果写进文件（票头 `Status`、Comments 或产物末尾的完成标记），这是准绳；初始提示里写了「总控会话」的 Claude 窗口，再用 `SendMessage` 提前通知一声。

## 2. 拆票

- 用 `/to-tickets` 把审定的 spec 拆成开发票，放在 `<阶段目录>/issues/`。spec 窗口可以直接拆。
- 同时写 `<阶段目录>/tickets-common.md`，各票只写本票特有的内容，公共部分引用它。它包含：
  - 读取路径（spec、开发计划、决策来源的绝对路径）；
  - 边界（可写目录、只读仓库、不得修改的共享模块）；
  - 风险与执行链；
  - 回归基准与测试命令；
  - 跨票的数据格式（一次定死）；
  - 公共文件归属表：并行的票不改同一个文件；
  - 拆票时发现的 spec 缺口，以及本阶段采用的结论；
  - 末尾留「总控修订」一节，总控或用户改判时在这里登记。
- 总控给每张票标风险（高 / 中 / 低），判定标准见参数文件。
- 总控排出批次和顺序：哪些票可以并行，哪些必须串行。
- 第一张票是在新基点上重建回归基线。
- 拆票窗口全部写完后，在 `tickets-common.md` 的最后单独写一行「拆票完成」，再通知总控；总控同样把 `tickets-common.md::拆票完成` 加进监视。
- 总控向用户汇报拆票结果，「执行」一栏写到具体模型。

## 3. 分支与 worktree

- 阶段分支：`<分支前缀><阶段>`，从参数文件中的 feature 分支（上一阶段合并后的状态）开出。集成 worktree：`<worktree 根目录>/<阶段>-integration`。
- 每张票：worktree 是 `<worktree 根目录>/<阶段>-<NN>`，分支是 `<分支前缀><阶段>-<NN>`，从阶段分支最新提交开出。由 `agent-loop ticket open <票> --prompt <提示文件>` 一次建好并开窗，不用手工执行 `git worktree add`。
- 参数文件列了本机专用文件时，`agent-loop ticket open` 建完 worktree 后把它们从主工作树复制进去。参数文件 `docs/agents/loop-profile.md` 只留主工作树一份，命令不会把它留在 worktree 里。窗口按主工作树的绝对路径读它。
- 任务目录等未纳入 Git 的文件在 worktree 里看不到：窗口一律按主工作树的绝对路径读取 spec、票、ADR、GLOSSARY，并且只在主工作树的位置修改票文件。

## 4. 按风险的两种做法

**高风险票（计划窗口 → 开发窗口）**

1. **计划窗口**（模型见参数文件「高风险计划」）：
   - Claude 模型用计划模式（`--permission-mode plan`）；其他模型没有计划模式，初始提示里写明「用户审定之前只读代码、不写任何文件」。
   - 按 [plan-format.md](plan-format.md) 出计划，测试先行的用例清单写到具体用例。交用户审批之前，先把「待明确 TODO」逐项问完，把结论写进计划，再出最终版本交用户审定。用户看了计划要求修改时，总控记一次 `agent-loop ledger plan-revise <票>`。
   - 用户审定后不实现：把计划存为 `<阶段目录>/plans/<NN>-plan.md`，在票的 `## Comments` 回报，票头改为 `Status: plan-approved`，通知总控，窗口结束。
2. **开发窗口**（模型见参数文件「开发」）：严格照已审定的计划实现，测试先行，在本地提交。Claude 窗口用 `/implement`；非 Claude 窗口按 [ticket-file-windows.md](ticket-file-windows.md) 启动，初始提示写明计划文件的路径。

**中、低风险票**：一个窗口做完计划、测试先行的开发和自查，不单独出计划。

两种做法都不做逐票审查，审查集中在阶段审计。修复票与普通票同一规则：高风险的先计划，中、低风险的直接改。

## 5. 开发窗口：完成、提交、回报

开发窗口一次只做一张票，工作在总控为它建的 worktree 和分支上。

1. **完成**：满足票的验收标准；本票相关的定向测试全部通过（范围见参数文件的验证流程）。每张票只跑定向测试，不跑全套，不启动应用实例。
2. **本地提交**：在本票分支上提交，只包含本票范围内的文件；本机专用文件、日志、包管理缓存不提交。
3. **更新票**：票头写 `Status: done`，在 `## Comments` 追加完成记录。
4. **回报总控**：回报写进票的 Comments，然后通知总控。回报内容：
   - 票名、分支、提交哈希；
   - 运行的测试命令和结果，以及与回归基准比对的结论；
   - 需要用户手工执行的脚本（[external-state.md](external-state.md)）；
   - 与 spec 或计划的偏差，未解决的待明确事项；
   - 遗留事项：没验证的项、因条件不具备跳过的验证（没有写「无」）；
   - 下一张票需要知道的前提。

完成标准：总控只凭回报内容，就能判断本票能否合入、下一张票能否开始。

## 6. 自动接续

完成的信号以票文件为准（票头 `Status`、文件末尾的完成标记），由监视发现；窗口发来的消息只是提前通知，可能因为窗口中断而发不出来。同一件事的信号先后到达两次时，后到的那次先查进展记录：这张票已经合入、或者下一个窗口已经开过，就不再处理。

**裁决的依据**：spec 和计划都经用户审定，两者冲突时以后审定的那份为准；总控按它裁决，在 spec 末尾追加修订记录，并在汇报里告诉用户。冲突涉及接口或业务取舍时，停下来问用户。

总控收到完成回报后：

1. **核对**：运行 `agent-loop ticket verify <票>`，它一次列出票头、票分支的提交、改动的文件、工作区是否干净和完成回报。你据此判断：提交只含本票范围内的文件；回报的测试结果是「无新增失败」。测试结论以完成回报为准：看里面的命令和通过、失败、跳过的数，回报不全就让窗口补。**你不重跑测试**，合入前后都一样：合入之后的结果由阶段审计窗口来审，合并窗口在推送前跑全量。总控不审代码。核对不通过、退回窗口重做时，记一次 `agent-loop ledger rework <票>`。
2. **合入**：运行 `agent-loop ticket merge <票>`。它把本票分支以 `--no-ff` 合入本地阶段分支，登记完成时间，并登记关窗（[ledger.md](ledger.md)）。全程在本地操作。它报告有冲突时已经撤销了这次合入，你停下来交给用户。合入后测试失败、退回重做的，同样记一次返工。
3. **整理**：回报里的遗留事项用 `agent-loop todo "<内容>" --must --by 总控` 记进待办清单；更新开发计划的进展记录和票状态，输出开窗清单。
4. **开下一个窗口**：按排好的顺序取下一张 `Blocked by` 已全部完成、与进行中的票没有文件归属冲突的票，不等用户确认直接开启：写好提示文件，运行 `agent-loop ticket open <票> --prompt <提示文件>`，并在进展记录里记一行「开窗」。命令会列出参数文件自上次开窗以来的变更，不用为此重读参数文件。每张开出去的票都在监视范围内，Claude 窗口的票也一样。参数文件填了窗口上限时，开着的窗口数不超过它。

**参数文件「自动接续」取「需确认」时**：做完第 1 步核对就停下，把核对结果、准备合入的票、准备开的窗口列给用户；用户在总控窗口确认后，再做第 2 到第 4 步。一次确认只管当时列出的这些票：之后再有票完成，重新列出、重新确认。取「自动」时不等确认，照上面四步直接做。这一项不分风险：高风险票的计划始终由用户审定，与它无关。

**「需确认」只管票完成之后**：它管的是「一张票做完，合入它、再开下一张票的窗口」之前的这次确认。用户直接提出的需求写成票之后，开这张票的第一个窗口不属于这种情况：没有东西要合入，用户提需求本身就是确认。这时不问用户，直接开窗，并在回复里写明开了哪个窗口、用的什么模型。需要停下来的只有各自有规则的那几种：与用户维护的文档或已有决定冲突、有几种做法要用户选定、要用户先执行脚本、高风险票的计划要用户审定。

**遇到以下情况停下，交给用户，不开下一个窗口：**
- 回报中有测试失败，或者有需要用户决定的待明确事项；
- 合入出现冲突；
- 下一张票依赖的脚本还没有由用户执行；
- 没有可以开始的票；
- 阶段的全部票都已完成：汇报阶段结果，进入收尾流程。

停下只针对受影响的票；其他互不依赖的票照常接续。

## 7. 阶段收尾

参数文件里关掉的环节跳过。

1. **收尾票**（模型见参数文件「收尾」）：跑一次全套回归（参数文件中的命令），与回归基准逐条比对；补齐部署说明和接口契约文档。收尾票不启动应用实例。
2. **阶段审计**：[stage-audit.md](stage-audit.md)。
3. **修复票**：按用户对审计结论的逐条决定开票，全部合入后再跑一次回归复核。此时阶段**代码完成**：总控运行 `agent-loop ledger snapshot`，在阶段汇报里附上 `agent-loop usage <阶段>` 输出的按模型汇总。
4. **合并窗口**：请用户同意合并时，一并列出待办清单里建议「合并前」处理的遗留（`agent-loop todo --due-now 合并前`），作为提醒；用户同意后开启，见 [merge-window.md](merge-window.md)。没有启用合并窗口的项目，阶段分支留在本地，由用户处理。
5. **回归测试**和下一阶段并行：[regression-test.md](regression-test.md)。合并推送之后，总控照常进入下一阶段：先请用户过一遍待办清单，再开下一阶段的 spec 窗口；下一阶段的阶段分支从合并后的 feature 分支开出。
6. **功能结束**（最后一个阶段完成之后）：展示待办清单里全部剩下的条目，请用户逐条表态；附上整个功能的 `agent-loop usage`。

## 8. 关窗与清理

**窗口**。每个窗口做完并回报后，最后告诉用户「本窗口的工作已结束，可以关闭」。总控在验收了这个窗口的结果之后登记关窗：参数文件「自动关窗」取「启用」时运行 `agent-loop window close <窗口编号|票号>` 关掉它，取「关闭」时加 `--record-only` 只登记。时点：

| 窗口 | 什么时候关 |
| --- | --- |
| 开发窗口 | 这张票合入之后 |
| 计划窗口 | 计划已审定、开发窗口已开出之后 |
| spec 和拆票窗口 | 拆票结果核对完之后 |
| 审计窗口 | 用户对审计结论逐条表态之后 |
| 合并窗口 | 总控核对推送结果之后 |

总控自己、规范维护窗口、错误对接窗口，以及正在等用户答复或等裁决的窗口，不自动关。关掉的会话可以按会话 ID 恢复。

**worktree**。每个 worktree 都有自己的一份源码、依赖和构建产物，不清理会很快占满磁盘，所以票合入之后它的 worktree 就清掉：

- 参数文件「自动清理worktree」取「启用」时，`agent-loop ticket merge` 在合入之后删掉这张票的 worktree。条件是工作区干净；只删 worktree，票分支保留，需要时用 `git worktree add <目录> <分支>` 重建。不满足条件时不删，命令会说明原因，不强制删除。
- 「自动关窗」取「关闭」时窗口由用户关，命令不在合入时删 worktree；窗口关掉之后运行 `agent-loop worktree prune`。
- `agent-loop worktree prune` 列出所有可以清理的票 worktree（分支已合入别的分支、工作区干净、没有窗口开着）和各自的大小，确认后删除。用它处理积压的。
- 阶段分支、修复分支的集成 worktree，以及测试用的 worktree 不清理；任务目录下的文档全部保留。

**分支**。票分支不随 worktree 删除。合并窗口推送成功之后，总控可以列出已经完整合入的票分支，用户同意后删除；没有完整合入的不删，单独列给用户。删分支每次都先列给用户。
