# 合并窗口：同步、合并、推送

阶段代码完成（修复票全部合入）、用户同意合入后，总控开合并窗口，工作目录是主工作树，模型见参数文件「合并」。修复分支修完后也走合并窗口（[after-release.md](after-release.md)）。

合并窗口获授权推送参数文件中列出的分支；除这些分支外，任何窗口都不推送。参数文件里同时有 feature 分支和共享环境分支时，合并分两轮，先 feature 后共享环境；只有 feature 分支时只做第 1 轮。

| 轮次 | 目标分支 | 合入来源 | 推送前验证 |
| --- | --- | --- | --- |
| 1 | feature 分支 | 阶段分支（或修复分支） | 见参数文件「验证流程」 |
| 2 | 共享环境分支 | 第 1 轮推送后的 feature 分支 | 见参数文件「验证流程」 |

## 每一轮的步骤

1. **同步远端**：`git fetch <远端>`，切到目标分支，执行 `git merge --ff-only <远端>/<目标分支>`，把本地追平远端。记下远端带来的他人提交，特别是改动共享模块、公共组件或数据库脚本的提交。远端还没有这个分支时（新仓库的第一次推送），这一步没有对象，跳过并在记录里写明；推送时会在远端新建这个分支。
2. **本地合并**：`git merge --no-ff <合入来源>`。
3. **处理冲突**：在本地解决，保留双方的意图；记下每个冲突文件和处理方式。
4. **验证**：按上表执行。
5. **推送**：`git push <远端> <目标分支>`。推送前确认待推送的提交中没有本机专用文件、日志和包管理缓存。
   这次合并里有「把某个文件移出 Git」的提交时，合并会把主工作树里的那份文件一起删掉。合并之后确认它还在；不在时从合并前的提交里取回来（`git show <合并前的提交>:<文件> > <文件>`），它已经在本机忽略规则里，不会再被跟踪。
6. **记录**：写一份合并报告 `<功能目录>/merges/merge-<NN>.md`（`<NN>` 接着已有的往后排，总控在初始提示里给出文件名），写明：合并前后的提交哈希、远端带来的他人提交、冲突及处理方式、验证结果、推送结果。全部轮次做完后，在报告的最后单独写一行「合并完成」，再通知总控。总控据此把要点记进开发计划的进展记录；合并窗口自己不改开发计划。

第 1 轮推送成功、验证无问题时，直接接着做第 2 轮。

验证范围里写的是「与收尾票的回归结果比对」而项目关掉了收尾票时，改为与「修复票全部合入后在阶段分支上跑的回归复核结果」比对。

## 停下来交给用户的情况

出现以下情况时停下，不继续推送，把停在哪一步、为什么写进合并报告，在报告的最后单独写一行「合并停止」，再通知总控：
- 处理冲突需要在业务含义上取舍（两边改了同一段逻辑，或者涉及共享模块、公共组件、数据库脚本），或者没有把握保留双方意图；
- 验证失败；
- 推送被拒，说明远端在此期间有新提交：回到第 1 步重新同步、合并、验证；同一轮第二次被拒时停下；
- 第 1 轮有任何问题时，不开始第 2 轮。

推送都用普通的 `git push`，已推送的历史保持原样。需要撤销时，由用户决定，用 `git revert` 生成新提交，再走一遍合并窗口。

## 推送共享环境分支之后

共享环境分支推送后是否自动部署，见参数文件。合并窗口在记录中列出以下内容，并告诉用户：
- 本次上线的功能，以及相关开关的默认取值；
- 可能影响共享环境上其他人的地方；
- 需要用户先在该环境执行的脚本；
- 待办清单里建议「上生产前」处理的遗留（`agent-loop todo --due-now 上生产前`），作为提醒。

推送完成后，回归测试开始，不阻塞下一阶段（[regression-test.md](regression-test.md)）。
