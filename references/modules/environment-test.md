# 环境验证模块

有运行环境的项目才启用这个模块，用来验证单元测试覆盖不到的组合行为：权限、端到端流程、前后端组合、和原型或设计稿的比对，以及只有运行中的实例才能确认的事项。默认在发布之后进行，**不阻塞**下一阶段。项目也可以在参数文件里把它设为发布前的关口。

## 被测版本

- 被测的是发布后目标分支上的合并提交（如果设为发布前关口，就是阶段分支的 HEAD）。
- 为被测版本建一个 detached 的测试 worktree：`<worktree 根目录>/<阶段>-test`。之后再有合入，也不影响被测的代码。
- 测试记录里写明被测 SHA。修复后重测时，把测试 worktree 切到新的提交，并在记录里写明新的 SHA。

## 测试流程

审计报告验收后，开一张测试流程票：`Deliverable: artifact`，`report` 角色，按项目路由选择引擎。它只读代码，只写 `<阶段目录>/reviews/env-test-plan.md`，最后一个非空行写 `LOOP-DONE <Run-id>`。内容包括：

- **被测代码**：分支、SHA（发布前写好的流程先留空，发布后由 `release` 角色补上）、测试 worktree 的路径。
- **启动方法**：后端、前端各自的启动命令、工作目录、配置文件位置、端口、启动参数（包括部署说明里的安全参数，以及每个测试项需要放开哪几个），联调方式，怎样确认启动成功，怎样停止。
- **前置条件**：要先执行的脚本、开关取值、账号和测试对象。
- **测试项**：每一项写明页面或接口、步骤、预期，并标明是**只读**还是**写入**。写入项还要写明影响到哪些数据、怎么撤销。
- **只有运行中的实例才能确认的事项**：来自审计报告的清单，以及验收时登记的跨边界「未验证项」。写明看哪条日志，或者需要用户查库提供哪些字段。
- **限制**：记录并行服务是否会干扰验证结果。例如，两个示例服务共用测试队列时，说明如何确认哪个服务消费了测试消息。

## 执行

由用户安排执行者（`test` 角色，交互运行）和运行细节，总控不自动开这个窗口。执行时的边界：

- **启动前由用户确认**：本地实例连接共享资源会带来什么影响、联调标识、需要的脚本已经执行。
- **默认带安全参数**：只为当前测试项放开需要的那几个参数，每放开一个都要用户确认。后台任务可能影响其他使用者时，先由用户确认它只处理指定的测试对象。
- **默认只读**：写入步骤每次都要用户确认，并且只操作指定的测试对象。
- **登录、切换账号、查库**都由用户完成。执行测试的会话不输入密码，也不保存凭据。
- **收尾**：停掉实例，确认端口已经释放。由用户确认没有留下会被后台任务继续处理的数据。

## 证据与记录

- 每一项都写明：页面或接口、步骤、预期、实际、结论（通过、失败，或者未验证以及原因），附上截图、日志片段或其他证据。
- 结论写进 `<阶段目录>/reviews/env-test.md`，最后一个非空行写 `LOOP-DONE <Run-id>`。是否通过由用户判定。
- 执行时发现问题不改代码，只记录复现步骤和证据。

完成标准：每个测试项都有证据和结论；每个写入步骤、每次放开参数，都有用户确认的记录。

## 发现问题之后

- 用户把问题告诉总控。总控从目标分支开修复票（`<前缀><阶段>-fix-<NN>`），按风险分线，优先于下一阶段的票。修完走发布模块，再重测受影响的项。
- 修复合入目标分支后，按 `git-worktree.md`「修复票与下一阶段」的规则，把修复带进下一阶段。
- 问题涉及接口契约、数据模型或设计变更的，总控评估下一阶段哪些票受影响，写进这些票的 Comments。需要改下一阶段 spec 的，交给用户决定。
- **上游关口**：用户判定环境验证通过之前，本阶段的代码保留在当前交付目标，后续发布目标按项目配置执行。这一步由用户掌握。
