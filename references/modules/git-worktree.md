# Git 工作区：基点、在途更新、串行集成

## 基点与持有者

- **基点**：每张票的 worktree 从阶段分支的某个提交开出，这个提交就是这张票的基点，记在票头的 `Branch` 字段旁，或者 Comments 的派工记录里。验收时，`git diff` 也以这个基点为准。
- **持有者**：worktree 在任何时刻只有一个持有者：
  - 有 worker 在跑时（`Run` 为 `dispatched`、`claimed`、`planning` 或 `needs-decision`），持有者是 worker；
  - 其他时候，持有者是总控。

  总控只在自己持有 worktree 时才修改它。

## 阶段分支前进后，在途票要不要更新

阶段分支每合入一张票，总控都逐张检查在途的票，判断它是否**真的用到**了新合入的提交。下列情况算用到：
- 在途票的 `Depends` 里有刚验收的票；
- 在途票的 `Touches` 和新合入的改动有重叠；
- 在途票需要用到新合入的接口、数据结构或共享样例。

**没有用到的票**：维持原来的基点，不做任何改动。

**用到了的票**，等 worker 交回 worktree 之后再更新。交回的时机是：worker 完成、提请裁决、异常退出，或者总控在裁决里要求它先停下：

| worktree 的状态 | 怎么更新 |
| --- | --- |
| 干净，而且本票还没有提交 | 快进到阶段分支的最新提交：`git merge --ff-only <阶段分支>` |
| 干净，本票已有提交 | 按项目的集成策略，把阶段分支合入票分支（`git merge --no-ff <阶段分支>`），或者 rebase。冲突时停下，交给用户 |
| 有未提交的工作 | 不动。在 Comments 写明需要更新，由当前持有者先提交或交接，之后再更新 |

更新之后：
- 在 Comments 记下新旧基点的 SHA；
- 之前的测试证据作废，需要重新跑：如果 worker 还在，就在送回的指示里写明；如果是重派，就写在提示里；
- 涉及两张票组合行为的，补一个联合用例。

## 串行集成

- 合入阶段分支，一次只做一张票：先 `loopctl … intent <Run-id>.merge`，再 `git merge --no-ff`，最后 `loopctl … result`。
- 合入之后，集成结果可能和票分支不一样，比如期间有其他票合入，或者解决过冲突。这时按 `verification.md`「集成」的规则，在集成后的提交上补跑定向测试。
- 两张票各自都验收通过，但合在一起冲突或者测试失败时：后合入的那张票回到返工（状态转换表 T8），并在 Comments 写明冲突的对象。

## 修复票与下一阶段

- 从已发布的目标分支开出的修复票（`<前缀><阶段>-fix-<NN>`），发布后由总控把目标分支合入下一阶段的阶段分支，把修复带过去。有冲突时停下，交给用户。
- 下一阶段里，已经在途的票，按上面「阶段分支前进后」的规则判断要不要更新。
