# 发布模块

有发布动作的项目才启用这个模块。发布动作包括：推送到共享分支、开 PR、部署，或者交接给运维。项目只在本地交付、或者只交付补丁的，跳过本模块。

发布由项目配置的 `release` 角色交互执行，工作目录是主工作树。

## 前提

开始发布前，以下条件都要满足：
- 修复票全部 `accepted`；
- 审计处置表中阻塞发布的条目全部处置完：发布票（`Kind: release`）在 `loop-state.sh` 里是 `dispatchable=yes`，也就是票目录里没有 `pending` 且 `blocks=release` 的外部前置。
- 用户已经同意发布；
- 本票生效规则里，有推送或发布的授权记录，写明目标和来源。

## 部署说明

在收尾票中写，发布前由总控核对。复用仓库现有的发布说明格式，只写本阶段**实际有变化**的内容：

- **脚本**：文件名、执行顺序（先执行再部署，还是先部署再执行；先部署会不会影响已经上线的功能）、执行环境、能否重复执行、怎么回退。
- **开关**：新增或修改的开关、默认值。区分运维开关和过渡开关：运维开关长期保留；过渡开关要写明清理条件和负责人。
- **安全参数**：启动或部署时需要的保护性参数，以及每个参数关闭的是什么。
- **回退**：代码回退用 `git revert`，再走一遍发布。数据和脚本的回退方式单独写。
- **对他人的影响**：会影响共享环境里其他人使用的地方。

写完部署说明，和获准发布是两件独立的事：说明写好了，不代表可以发布。

## 发布步骤

参数文件按顺序列出已授权的发布目标。每个目标可以是分支，也可以是 PR。每个目标依次执行：

1. **再核对授权**：重读本票生效规则，确认对这个目标的授权仍然有效、目标没有变化。授权被撤销或目标已变时，停下并提请裁决。不能用旧的批准去推送一个新的目标。
2. **同步远端**：`git fetch origin`，切到目标分支，`git merge --ff-only origin/<目标分支>`。记下远端带来的他人提交，特别是改了共享模块或脚本的那些。
3. **本地合并**：`loopctl … intent <Run-id>.release.<目标> release "<来源>-><目标>"`，然后 `git merge --no-ff <来源>`。来源是阶段分支，或者上一个已推送的目标。
4. **处理冲突**：在本地解决冲突，保留双方的意图，逐个记下冲突文件和处理方式。冲突需要在业务含义上取舍时，停下交给用户。
5. **推送前验证**：按参数文件对这个目标的要求执行。验证失败时停下。
6. **推送**：用普通的 `git push origin <目标分支>`，或者开 PR。推送前确认待推送的提交里没有本机专用文件。推送被拒，说明远端在此期间有新提交，回到第 2 步；同一个目标第二次被拒时，停下。
7. **记录**：`loopctl … result <Run-id>.release.<目标> <推送后的 SHA>`。在进展记录中写明：合并前后的 SHA、他人的提交、冲突怎么处理的、验证结果、推送结果。

上一个目标推送成功、验证通过后，再做下一个。前一个目标有任何问题，都不开始下一个。

推送一律用普通推送，已推送的历史保持原样。需要撤销时，由用户决定，用 `git revert` 生成新提交，再发布一次。

## 发布后

推送会自动部署到共享环境时，告诉用户三件事：
- 上线了哪些功能、开关的默认值；
- 可能影响他人的地方；
- 需要先执行的脚本。

需要用户执行的脚本，在下一个依赖它的环节上写成外部前置（`External-<ID>: pending blocks=…`），用户确认执行后改为 `met`。没执行完的脚本，只阻塞依赖它的部署或验证，不影响其他工作。

有环境验证的项目，把被测提交的 SHA 补进测试流程文档（见 `environment-test.md`）。
