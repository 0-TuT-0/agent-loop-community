# 阶段流水线

每个阶段都走这条流水线，参数文件可以关掉其中某一步。每一步都是一张票（或者一份带完成标记的报告），同样由主循环派工和监视。各环节的引擎和模型按[项目路由](../routing.md)选择。

```
spec → 拆票 → 开发票循环 → 收尾回归 → 独立审计 → 按风险处理修复票
→ 代码完成 → 发布 ┬─▶ 环境验证（默认不阻塞下一阶段）
                 └─▶ 下一阶段
```

Git 工作区相关的规则（基点、在途 worktree 的更新、串行集成）见 [git-worktree.md](git-worktree.md)。

## 0. spec

- 由规划窗口在阶段基点所在的集成 worktree 与用户讨论。它只读代码，产出 `<阶段目录>/spec.md`。
- spec 必须承接**跨阶段承诺**：逐条读开发计划里的跨阶段前提和前序阶段的延期项（见「4. 审计」处置表的「延期到」），对每一条都写明处置方式：继承、替代（被哪一条取代）或继续延期（延到哪个阶段、理由）。不能静默丢掉。
- 用户审定 spec，审定记录写在 spec 末尾。审定之后才能拆票。

完成标准：每一条跨阶段承诺在 spec 里都有处置记录。

## 1. 拆票

用原规划窗口或新规划窗口把审定后的 spec 拆成票。拆票窗口先读代码，核对 spec 和现状，然后产出以下内容。

### 1.1 票

- 每张票写在 `<阶段目录>/issues/<ID>-<名称>.md`，票头按 [../../templates/ticket.md](../../templates/ticket.md) 填写：`Deliverable`、精确的 `Depends`、`Touches`、`External-<ID>`。使用外部拆票工具生成的票，拆完后按模板逐张补齐：依赖说明移到「依赖说明」一节，`Depends` 只写 ID。
- 总控运行 `loop-state.sh`，确认没有任何 `unknown-dep` 之后，才进入循环。
- 拆票后，由总控给每张票标 `Risk`，高风险票写上 `Plan: required`；再排出批次：哪些票可以并行，主链按什么顺序串行。
- 第一张票通常是在新基点上重建回归基准，用 `Deliverable: artifact`。

### 1.2 `tickets-common.md`

- 各票的公共约定、读取路径、回归基准与测试命令。
- **公共文件归属表**：每个会被多张票改动的文件，写明归哪张票改，其他票只读或者通过裁决协调。
- **真实调用方**：每个被改动的接口、函数或数据结构，列出代码里现有的调用方（用搜索得出，写明路径）。如果 spec 漏掉了某个调用方，就记入 1.3 的出入登记。
- **共享样例**：多张票共用的契约样例（接口返回、文件格式），写明由哪张票提供、哪些票消费，以及来源（真实数据或权威定义）。

### 1.3 出入登记 `<阶段目录>/spec-gaps.md`

spec 和代码现状的每一处出入，都登记一条：

| ID | 现状证据（路径、行号） | 冲突的 spec 条款 | 受影响的票 | 决定权 | 结论 |
| --- | --- | --- | --- | --- | --- |
| G1 | | | | 总控 / 用户 | |

- **总控决定**：按已审定的 spec 就能确定的，例如文件归属、实现位置、命名。总控在「结论」中写明依据。
- **用户决定**：涉及业务语义、对外契约、验收标准变化的。交给用户逐条答复，答复写进「结论」，同时写进受影响票的 Comments。
- 还没有结论的项，在受影响的票上写 `External-G<n>: pending blocks=dispatch 等待出入 G<n> 的结论`。有了结论，就改为 `met`。

### 1.4 外部需求登记 `<阶段目录>/external-requirements.md`

本仓库做不到、必须由只读仓库、上游服务或其他团队提供的能力，不在本仓库实现，而是登记成需求，交给用户去协商：

| ID | 需要什么 | 已核对过的现有能力 | 为什么本仓库做不到 | 消费的票 | 能否降级，降级时如何展示 | 解除条件 | 状态 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| R1 | | | | | | | 待协商 |

- 同一个能力被多张票消费时，只登记一个 ID，各票引用同一个 ID。
- 允许降级的票照常开发，按降级方式交付，票头写 `External-R<n>: pending blocks=release`，只阻塞发布。
- 不允许降级的票，写 `External-R<n>: pending blocks=dispatch`。
- 用户协商有结果后，更新状态和受影响的票。

完成标准：每张票的票头字段都填全；`spec-gaps.md` 里每一项都标明了决定权；每个外部能力都只登记一次。

## 2. 开发票循环

按 SKILL.md 的「循环」执行。阶段分支 `<前缀><阶段>` 从阶段基点开出。

## 3. 收尾

- 由实现窗口接一张收尾票。
- 跑参数文件里的全套回归命令，在阶段分支 HEAD 上与回归基准逐条比对，比对的是失败用例的标识。
- 有发布动作的项目，按 [release.md](release.md)「部署说明」补齐部署说明和接口文档。
- 收尾票只跑测试、写文档，不启动连接共享环境的实例。

## 4. 审计

- 使用项目为审计配置的独立模型，与实现模型区分。引擎支持时按路由设置较高的推理强度，并在启动参数中显式传入。工作目录是阶段集成 worktree。
- 审计是一张 `Deliverable: artifact` 的票，`report` 角色。报告写入 `<阶段目录>/reviews/stage-audit.md`，最后一个非空行写 `LOOP-DONE <Run-id>`。初始提示要写明：只读代码，只写这一份报告，不提交，不推送，不碰外部状态。
- **审查范围**：阶段分支相对基点的整体 diff，对照以下内容：
  - spec 和它的修订记录；
  - 计划；
  - 各票 Comments 里的偏差和裁决；
  - 参数文件中的隔离要求；
  - 回归基准；
  - `spec-gaps.md`、`external-requirements.md`。

  另外两个重点：一是**抽查总控的裁决**，找出实际改变了验收口径、却没有经过用户的裁决；二是**跨边界的组合行为**，即两边测试各自通过、但用的是同一份自造样例的情况。
- **每条发现**都有编号（`A1`、`A2`…），写明级别（阻塞 / 应修 / 建议）、位置、问题、建议的修法，以及阻塞哪个关口（发布、下一阶段，或者不阻塞）。报告给出总体结论，并附一份「只有运行中的实例才能确认的事项」清单，交给环境验证使用。

### 4.1 处置表（审计闭环）

报告验收后，总控在报告末尾追加处置表，并把发现逐条交给用户决定：

| 发现 | 级别 | 用户决定 | 决定人和时间 | 修复票 | 复验证据 | 延期到 | 阻塞的关口 | 状态 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| A1 | 阻塞 | 现在修 / 延期 / 接受 | | | | | 发布 | 待决定 |

- **分批推进**：用户决定了哪几条，就先为这几条开修复票；还没决定的条目保持「待决定」，不影响已经获批的修复。
- **修复票**：按风险分线，高风险票先交规划窗口，用户审定计划后交实现窗口；其余由实现窗口直接处理。修复票验收时，在「复验证据」一栏写明证据：修复票的 `Accepted` 和针对这条发现的测试。
- **延期**：写明延到哪个阶段。同时把这一条加进开发计划的跨阶段前提，下一阶段的 spec 必须处置它。
- **关口**：每一条「阻塞发布」、还没有结论或修复的发现，都在审计票上写 `External-A<n>: pending blocks=release`，处置完成后改为 `met`。发布票（`Kind: release`）会被所有这类条目阻塞，`loop-state.sh` 的 `reason` 一栏直接列出还缺哪一条（`release-gate:A<n>@<票>`）。

完成标准：每条发现都有处置结论；每条「现在修」的发现都有修复票和复验证据；每条延期的发现都出现在跨阶段前提里。

## 5. 发布与环境验证

修复票全部 `accepted`，处置表中阻塞发布的条目全部处置完，用户同意后，按 [release.md](release.md) 发布。项目没有发布动作时，阶段在这里结束，交付物就是阶段分支，或者约定的产物。

有运行环境的项目，发布后按 [environment-test.md](environment-test.md) 做环境验证。它不阻塞下一阶段。

## 6. 下一阶段

发布完成、用户确认阶段结果后，开下一阶段的 spec。下一阶段的阶段分支，从发布后的目标分支开出；没有发布的项目，从本阶段分支开出。
