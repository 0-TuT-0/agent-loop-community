# 回归测试

功能测试在合并窗口推送之后做，**不阻塞合并窗口，也不阻塞后续开发**。单元和组件回归照旧在开发票和收尾票里用脚本跑。测试方式见参数文件，默认是「统一回归」。

目标是让每个测试项都能得出结论，并且不在测不了的项上花 token。所以前提在写测试项之前确认，测试项一个场景一项，没测的项有去向。

## 时机与分工（两种方式都适用）

- **先合并，后测试**：合并窗口不等测试；推送完成后再开始测试。
- **下一阶段照常开始**：阶段代码完成、合并推送之后，总控照常进入下一阶段。
- **谁写、谁执行**：测试文档由测试文档编写窗口写（模型见参数文件「写测试流程」），总控自己不写测试项。测试由用户在一个单独的执行窗口里亲自操控着做。**总控自己不执行测试**，也不在总控窗口里逐项问用户、替用户登记结果；用户说开始回归时，总控开执行窗口（第 3 步）。
- **往上游合由用户掌握**：总控汇报是否还有未修复的失败项；代码是否从 feature 分支继续往上游合（预发、生产或上游集成分支），由用户自己决定。

## 文件

统一回归的文档按阶段分文件，放在 `<功能目录>/regression/`：

| 文件 | 内容 |
| --- | --- |
| `background.md` | 给执行者的背景说明，整个功能一份：系统怎么分层、数据存在哪里、各部分靠哪些标识对应、常见误区、资料索引。每个阶段追加 |
| `<阶段>-prereq.md` | 这个阶段的前提清单，以及用户对每条的表态 |
| `<阶段>-plan.md` | 这个阶段的测试项 |
| `<阶段>-result.md` | 这个阶段的结果，每一轮追加一节 |
| `summary.md` | 各阶段的统计，由 `agent-loop regress` 生成 |
| `issues-log.md` | 错误对接窗口的问题记录（[optional-windows.md](optional-windows.md)） |

执行窗口测哪个阶段，就只读那个阶段的文件和 `background.md`。

## 第 1 步：前提清单

编写窗口只读代码和 spec，先写 `<阶段>-prereq.md`，写完在末尾单独写一行「前提清单已写完」，然后停下。总控把这个标记加进监视，发现后把清单交给用户。

前提清单分四类，每条注明有多少测试项依赖它：

| 类别 | 写什么 |
| --- | --- |
| 账号 | 需要哪几种权限的账号，各用来验证什么 |
| 数据 | 需要哪些已有的记录或样本 |
| 脚本和开关 | 需要先执行的脚本、开关的取值 |
| 写操作 | 需要在共享环境上修改数据的操作：页面、按钮、对象、预期结果、怎么撤销 |

用户对每条表态，总控把表态写进 `<阶段>-prereq.md`：

| 表态 | 后果 |
| --- | --- |
| 已具备 | 依赖它的测试项照常写 |
| 可以准备 | 照常写。总控记一条遗留，写明要在执行测试之前准备好（[todo.md](todo.md)） |
| 准备不了 | 依赖它的测试项标为「不测」并写明原因。以后可能具备的，总控记一条遗留，留待补测 |

## 第 2 步：测试项

用户表态之后，总控让同一个编写窗口接着写 `<阶段>-plan.md`，写完在末尾单独写一行「已完成」。怎么让窗口继续，见 [ticket-file-windows.md](ticket-file-windows.md)「送回窗口」。

**一个场景一项**：一项只有一个账号、一个操作路径、一个预期结果。判断标准：这一项能不能只用「通过」或「失败」回答。需要写成「A 账号通过、另一个账号待补」的，拆成两项。

**分级**：每项标「必测」或「选测」。

- 必测：spec 里的每条验收标准至少对应一项必测；关系到数据正确性、权限、对其他功能的影响的项也是必测。
- 选测：同一条验收标准的其他账号、其他分辨率、边界情况。
- 级别由编写窗口提出；用户看测试计划时可以改。

**格式**：每个测试项是表格的一行，前两列固定是编号和级别，命令靠这两列统计。编号稳定，已有的编号不改：

```markdown
| 编号 | 级别 | 前提 | 页面与步骤 | 预期结果 | 只读 / 写入 |
| --- | --- | --- | --- | --- | --- |
| P3-014 | 必测 | 管理员账号 | …… | …… | 只读 |
```

因前提准备不了而排除的项也写在表里，在「前提」一栏写明「不测：<原因>」，并在第一轮结果里记为「不测」。

测试计划另列：需要看的日志关键字和只读查询语句、不测的事项。写作依据：这个阶段的 spec、部署说明、审计报告里的验证清单、项目规范。

**编写窗口的边界**（写进初始提示）：只读代码；只写 `regression/` 下这个阶段的文档和 `background.md`；不改代码、不提交、不推送、不启动实例、不连数据库、不调共享环境的接口。

## 第 3 步：执行

**开执行窗口**：用户说开始回归时，总控写好初始提示，运行 `agent-loop window open --step regress --stage <阶段> --dir <主工作树> --prompt <提示文件>`（模型取参数文件「测试流程模型」，用户指定了别的就加 `--model`）。初始提示写明：

- 测哪个阶段、被测提交；只读这个阶段的 `<阶段>-prereq.md`、`<阶段>-plan.md` 和 `background.md`，照本文件第 3 步执行；
- 下面「执行时的边界」；只写 `<阶段>-result.md`（和需要时的 `manual-handoff.md`），不改代码、不提交、不推送；
- 用户就在这个窗口里操作和回答；发现的问题记在结果里，不自己开票、不自己修；
- 一轮做完，在结果文件末尾单独写一行「第 <N> 轮已完成」，然后停下。

执行窗口的用量单独登记。监视看到「第 <N> 轮已完成」后总控被唤醒，照第 4 步收口，然后关掉执行窗口；下一轮（补测、修复后重测）另开。

执行时用户告诉执行窗口这一轮测到哪一级，默认只测必测。执行窗口只做前提已具备的项；前提还没准备好的项记「未测」并写明缺什么，不去尝试。

结果写在 `<阶段>-result.md`，每一轮一节，前两列固定是编号和结论：

```markdown
## 第 1 轮（<日期>，被测提交 <哈希>）

| 编号 | 结论 | 证据 | 问题编号 |
| --- | --- | --- | --- |
| P3-014 | 通过 | …… | |
```

结论只有四种：

| 结论 | 含义 |
| --- | --- |
| 通过 | 实际结果与预期一致，有证据 |
| 失败 | 实际结果与预期不一致，登记问题 |
| 未测 | 应该测但这一轮没做，写明原因 |
| 不测 | 因前提准备不了而排除，或用户决定不测 |

**执行时的边界**：

- **共享环境默认只读**：浏览、展开、切换页签、查看详情、截图。
- **写操作先确认**：保存、发布、启停、授权、删除、推送等会修改共享数据。前提清单把写操作逐项列出，执行前由用户确认，只操作用户指定的测试对象。
- **不为测试改环境的配置和开关**；需要改时由用户决定并操作。
- **登录和切换账号由用户完成**：执行测试的会话不输入密码，也不保存凭据。
- **日志和查库由用户提供**：执行者看不到共享环境的后端日志，文档给出要搜的关键字和只读查询语句。
- **交接**：执行者测到一半要交给用户手工继续时，写一份 `manual-handoff.md`：现场留下的数据、已有证据、每一项还缺什么。

## 第 4 步：收口

一轮结果出来后（结果文件末尾出现「第 <N> 轮已完成」），总控运行 `agent-loop regress`。它更新 `summary.md`，并打印每个阶段一行状态和失败、未测的编号，例如：

```
p3 回归：必测 28 项，通过 24、失败 1、未测 3、不测 0、未执行 0；选测 18 项，通过 0、失败 0、未测 0、不测 0、未执行 18
```

总控把这行状态汇报给用户，然后按结论处理：

| 结论 | 去向 |
| --- | --- |
| 通过、不测 | 结束 |
| 失败 | 登记问题，照 [after-release.md](after-release.md) 开修复票，票里写明对应的测试项编号 |
| 未测 | 记一条遗留，写明缺什么；同一个原因的几项合成一条，例如「等 U2 账号后补测 p3 的 12 项」。补测完成后关闭这条遗留 |

**没有失败项时，汇报完这行状态，这个阶段的回归就结束了**，不需要用户另外表态。有失败项时才进入修复。

**复测**：修复票合并推送之后，只复测它对应的测试项，加上修复票的计划里写明可能受影响的项，不重跑整份计划。结果追加成新的一轮，前面各轮的结论保留；统计以每个编号最后一次的结论为准。

完成标准：每个必测项都有结论；失败项都开了修复票；未测项都在待办清单里；用户收到了状态汇报。

## 每阶段本地测试（备选）

参数文件选了这种方式时，每个阶段做一次：用合并后的 feature 分支代码，在本机启动应用来测。这样能直接看到终端里的报错和日志。前提清单、测试项的写法、结论和收口都与统一回归相同，不同之处：

- **被测版本**：合并窗口推送后 feature 分支上的合并提交。总控为它建一个测试专用 worktree：`<worktree 根目录>/<阶段>-test`，detached 到这个提交。合并窗口把提交哈希补进测试文档。
- **文档**：除测试项外，`<阶段>-plan.md` 还要写：启动方法与文件位置（命令、工作目录、端口、启动参数、怎么确认启动成功、怎么停止）、前置条件（要先执行的脚本、开关取值、账号和测试对象）、只有运行中的实例才能确认的事项、本地实例与共享环境并存带来的限制。
- **执行时的边界**：上面的边界都适用，另加：
  - 每次启动前由用户确认联调标识、本地实例连接共享库的影响、所需脚本已执行；
  - 默认带部署说明里的安全参数启动，只为当前测试项放开需要的那几项，每放开一项都先经用户确认；
  - 测试结束后停掉应用，确认端口已释放；由用户查库确认没有留下会被后台任务继续处理的数据。
