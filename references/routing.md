# 路由与分工

项目在 [profile](../templates/profile.md) 中为启用的环节指定引擎、模型和适用的推理强度。引擎名称对应本机 `machine.md` 的引擎适配表。总控在首次派工前核实实际可用的模型、权限和交互方式；有环节缺少合适的引擎时，将该环节和缺少的能力告知用户。

## 默认分工

| 环节 | 如何选择执行者 | 工作方式 |
| --- | --- | --- |
| 总控 | 能处理调度、协调和授权边界的会话 | 派工、裁决分工、核对证据、合入 |
| 阶段 spec | 能与用户讨论方案的规划窗口 | 只读代码，写 `spec.md`，交给用户审定 |
| 拆票 | 熟悉当前 spec 的规划窗口 | 写票和 `tickets-common.md`，明确公共文件归属 |
| 高风险票的计划 | 能交互审定计划的规划窗口 | 按[计划格式](plan-format.md)提出方案。审定后将计划写入 `plans/<ID>-plan.md` |
| 高风险票的开发 | 有能力执行已审定计划的实现窗口 | 测试先行，核对计划版本，在本地提交 |
| 中低风险票 | 通用实现窗口 | 在同一窗口里计划、开发、自查，通过票文件提请裁决 |
| 收尾 | 能运行项目回归命令的实现窗口 | 运行全套回归，与基准比对，补齐交付文档 |
| 阶段审计 | 与实现使用不同模型的审计窗口 | 只读审查整个阶段的差异，写独立报告。显式设置项目配置的推理强度 |
| 审计后的修复 | 按票的风险选择规划和实现窗口 | 高风险票先由用户审定计划，中低风险票直接开发 |
| 发布 | 获准执行发布流程的交互窗口 | 按[发布模块](modules/release.md)同步、合并并推送到已授权目标 |
| 测试流程编写 | 能根据发布内容设计验证步骤的报告窗口 | 只读代码，只交付 [环境测试流程](modules/environment-test.md) |
| 测试执行 | 由用户安排的交互测试窗口 | 在指定版本和环境运行测试，逐项留下证据 |
| 测试发现问题后的修复 | 按票的风险选择执行者 | 从已合并分支开修复票，排在下一阶段的票之前 |

表中的“规划窗口”“审计窗口”等说明环节分工。票头 `Role` 仍使用[票文件协议](protocol.md)定义的值，例如高风险计划写 `plan`，审计报告写 `report`。

## 风险判定

拆票后，由总控给每张票标注 `Risk`。判定标准写在参数文件中；没写时，满足任一条即为 `high`：
- 改动共享模块、公共组件，或其他团队的业务流程；
- 写入共享表，或做数据迁移；
- 改变现有接口的行为（放行或拒绝的逻辑、返回结构）；
- 改动线上开关的默认值。

`high` 走「计划 → 用户审定 → 开发」两步（状态机见 `protocol.md`）；`medium` 和 `low` 由一个 worker 做完。

## 升级

升级是指：把中低风险票改走高风险的两步流程，或者换用更强的模型。在两种情况下进行：
- 票进入 `paused`（状态转换表 T12：同一张票第二次异常，或者返工后验收仍不通过），用户决定升级（T13）；
- worker 提请的裁决显示，这张票的难度明显高于标注的风险，总控在裁决中提出升级，并由用户确认。

重新派工前，在 Comments 里写明升级的原因。

升级后的 worker 从已有提交和 Comments 接着做，不从头开始。
