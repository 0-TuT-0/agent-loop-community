# 阶段审计

阶段的全部票（包括收尾票）都合入阶段分支后，总控开阶段审计窗口，模型见参数文件「审计」。

- **工作目录**：阶段集成 worktree。
- **审什么**：阶段分支相对阶段基点的整体 diff，对照以下内容：
  - spec（包括审定记录）；
  - 各票的计划和 Comments 中的偏差记录；
  - 参数文件列出的隔离要求（例如不得改动的共享模块）；
  - 回归基线。
- **结论**：分为阻塞、应修、建议三级，每条写明位置、问题、建议的修法和影响。写入 `<阶段目录>/reviews/stage-audit.md`，并给出总体结论：通过、修复后通过、不通过。
- **审计报告附带的验证清单**：列出只有运行中的实例才能确认的事项，交给测试文档编写窗口使用。
- **初始提示要写全的边界**：只读代码；只写 `stage-audit.md` 这一个文件；不改代码、不提交、不推送、不启动实例、不连数据库、不调共享环境的接口；需要裁决时，照 `ticket-file-windows.md` 的「提请裁决」处理。
- **完成**：在报告末尾写「审计完成」。总控把这个文件加入监视范围。

## 审计完成之后

1. 总控把结论交给用户。阻塞项和应修项由用户逐条决定：现在修、推迟到哪个阶段，还是不修。用户的决定记在报告末尾的「用户决定」中。
2. 总控把每条问题归到引入它的票上，记进票台账：`agent-loop ledger audit <票> <严重程度>=<数量> ...`；归不到单张票的记在阶段名下。不修和推迟的也计数（[ledger.md](ledger.md)「怎么算」）。用户决定推迟的问题，另记一条遗留：`agent-loop todo "<问题>" --must --by 总控`。
3. 按决定开修复票，并用 `agent-loop ledger source <修复票> <来源票>` 注明它修的是哪张票的问题。修复票与普通票同一规则：高风险的先计划，中、低风险的直接改；修复票之间有依赖时写明 `Blocked by`。
4. 同时开测试文档编写窗口（`regression-test.md`），它会用到审计报告里的验证清单。
5. 修复票全部合入、回归复核通过后，阶段代码完成，等待用户同意开合并窗口。

发布之后的大需求也用这套方式单独审计一次，审的是那张票的分支相对它的基点的 diff（`after-release.md`）。
