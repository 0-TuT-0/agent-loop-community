# 待办清单

待办清单收「现在不做、以后要有人回来处理」的事，一个功能一份：`<功能目录>/todo.md`。它由 `agent-loop todo` 命令维护，总控和用户都不手工编辑。

## 收什么

只收**不卡当前任何一张票**的事。卡着某张票的事（等用户执行脚本、等裁决、等审定计划、进行中的票的结果）只出现在开窗清单里，不进待办清单。要立刻生效的事（叫停一张做错的票、裁决、撤销授权）由用户直接对总控说。

| 类别 | 含义 | 例子 |
| --- | --- | --- |
| 遗留 | 现在不做，以后必须做 | 需要真实数据才能做的实测；上线前的检查；清理临时 Key；用户决定推迟修的审计问题；因前提不具备而没测的测试项 |
| 想法 | 现在不做，以后做不做还没定 | 开发中用户想到的新点子；被选择跳过的事项 |

遗留必须有人关掉；想法可以被否决。

## 怎么记

| 谁 | 怎么记 |
| --- | --- |
| 用户 | 终端运行 `agent-loop todo "<内容>"`（记成想法），加 `--must` 记成遗留 |
| 用户对总控说「记一条：……」 | 总控运行同一条命令，加 `--by 用户`，内容照录用户的原话，不改写 |
| 总控 | 出现下面的情况时自己记遗留，加 `--by 总控` |

总控自己记遗留的情况：

- 用户决定推迟某条审计问题；
- 票的回报里写了没验证的项；
- 某项验证因条件不具备被跳过；
- 测试前提里用户表态「可以准备」的条目，以及测试结果里的「未测」项（[regression-test.md](regression-test.md)）。

其他窗口不直接写清单。它们把没做完的事写在回报里，由总控在合入时记。

**建议时限**：总控记遗留时用 `--due` 推荐一个时限：`合并前`、`功能结束前`、`上生产前`，没有明显时限的不填。时限只是提醒，没有约束力，是否执行由用户决定；用户可以让总控用 `agent-loop todo due <编号> <时限>` 改掉。

## 什么时候展示

| 场合 | 展示什么 |
| --- | --- |
| 总控的每次回复 | 开窗清单后面附一行 `agent-loop todo --count` 的输出，例如「待办：遗留 3 条（1 条建议合并前处理）、想法 5 条」；清单为空时省略 |
| 本次回复里清单有变化 | 在那一行下面列出新增或关闭的条目，各一行 |
| 每个阶段开始之前（含第一个阶段） | 展示全部未处理的条目（`agent-loop todo`），请用户逐条表态 |
| 请用户同意合并时 | 一并列出建议「合并前」处理的遗留（`agent-loop todo --due-now 合并前`），作为提醒 |
| 合并窗口推送之后的说明 | 列出建议「上生产前」处理的遗留 |
| 功能结束时 | 展示全部剩下的条目，请用户逐条表态 |
| 用户说「过一遍待办」 | 展示全部未处理的条目，请用户逐条表态 |

到了建议时限而条目没关，总控只在上表的场合把它列出来，不为此多停一次，也不拦着流程。用户没有对它表态时照常往下走，条目保持未关，下一个场合继续列出。

## 逐条表态之后

总控对每条给出建议的去向和理由，由用户决定，然后运行 `agent-loop todo close <编号> --to <去向> "<说明>"`：

| 去向 | 写法 | 适用 |
| --- | --- | --- |
| 并入下一阶段的 spec | `--to spec` | 属于后面某个阶段的范围。总控在给 spec 窗口的提示里列出这些条目 |
| 开成一张票 | `--to ticket` | 现在就该做：当前阶段的票，或者已发布功能修复分支上的票 |
| 另开一个功能 | `--to feature` | 想法比较大，和当前功能互不依赖 |
| 已完成 | `--to done` | 遗留的事做完了 |
| 不做 | `--to drop` | 用户否决。遗留条目要这样关闭时，说明里必须写用户说的原因 |
| 继续留着 | `--to keep` | 现在定不了，下个场合再看；条目保持未处理 |

关闭和转出的条目保留在文件里并标明去向，以后可以查到某个想法后来变成了什么。

## 与需求入口的关系

清单不是新的需求入口。想法进清单时只是记录，不触发任何开发；它变成需求，是在用户过清单时表态的那一刻，这属于「用户直接对总控说」。

完成标准：每条遗留都有记录人和时间；总控的每次回复里有一行统计（清单非空时）；每个阶段开始之前用户看过全部未处理的条目。
